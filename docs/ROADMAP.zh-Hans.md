## 2. 这个项目一开始的计划，以及它后来怎么了

起点是对上游的两条结构性不满，和一个打算同时回答这两条的设计。

**一：一个永不停下的浏览器。** 为了一分钟才变一次的内容常驻一个 WebContent 进程——时钟、天气、日历、
仪表盘。

**二：它不是真正的壁纸。** 一个位于 `.desktop` 层的无边框透明窗口。上游自己的 FAQ 承认了后果：菜单栏
取不到它的颜色。由此往下：Mission Control 手势会露馅（Plash#182）、Stage Manager 把它当窗口，以及
`DesktopWindow.swift` 里那一串 `collectionBehavior` 补丁。

答案是两套后端：一套 `snapshot`，把页面离屏渲染、拍成照片，然后放掉 web 进程——照片进窗口的
layer，或者（**A2**）经 `NSWorkspace.setDesktopImageURL` 成为一张真正的 macOS 壁纸；一套 `live`，也
就是现在这个常驻 web view，留给真的会动的页面。

**一样都没活下来，而原因值得留着：**

| 当时的断言 | 实际发现 |
|---|---|
| 快照渲染器可以给任意页面拍照 | 它拍不了那些有意思的页面。不在屏幕上的窗口会让 WebKit 报 `visibilityState: hidden`，于是 `requestAnimationFrame` 永远不跑，任何往 canvas 上画的东西拍出来都是空白。在一个页面上实测：离屏时 `canvas=none`，4 个 tile，232KB；在屏幕上时 `canvas=2790×1538`，44 个 tile，2452KB。用 JavaScript 覆盖 `document.hidden` 也没用——决定发生在它下面 |
| 两套后端可以共存 | 每一套都拥有「此刻在渲染什么」这个答案，而浏览模式改的正是这个。进浏览模式会重载，出来再重载一次，两次期间都露出桌面，而一次快照完成可能把页面从正在读它的人手里抽走。每修一个就露出下一个 |
| 菜单栏问题需要一张真壁纸 | 不需要。把页面挡在菜单栏那一条之外，用一条不透明色带取网站的颜色，这就是所有人真正想要的那部分 |

于是这套机器被拿了出来——两次移除加起来约 2400 行，§4 里的 811 行是其中一次——app 回到上游的做法：
一个 live 页面，只在被禁用、屏幕锁定或用电池时停。**A2 现在是直接拒绝；见 X8。** 省电按第 4 节的条件
一次放回一件，围着这个 live 页面做，而不是取代它。

## 4. 省电（P 系列）

> **这一整套目前都不在代码里。** 两套渲染后端、遮挡测量和静止画面自动识别都做过，而每一样都拥有
> 「此刻在渲染什么」这个答案——第 2 节里那场冲突，外加一条：禁用之后会留下一条色带。每一条都能修，
> 每修一条又露出下一条。
>
> 于是它出来了——811 行。交互就是这个 app 本身；省电是对它的优化，而且这份收益从没被干净地测过。
> 它一次放回一件，每件先有测量，也要有关掉它的办法。放回任何一件之前必须先成立的条件：
>
> 1. 对它声称能省掉的开销做一次测量，在机器其余部分空闲时进行，针对它真正瞄准的状态——一张被盖住
>    的壁纸，而不是一次浏览会话。
> 2. 「此刻在渲染什么」只能有一个主人。浏览模式会改这个答案，正是这个 case 弄坏了它的每一个版本。
> 3. 一个不需要理解它就能把它关掉的开关。

上游只因三件事停下：手动禁用、屏幕锁定、用电池。**完全没有任何关于遮挡的处理**，而这就是上面任何一
样都得赢过的基线。

**其中两个想法是拒绝而不是延后**，而它们正是背后从来没有 issue 的那两个。*内容铺满屏幕时转为不透明*：省下的东西测不出来，而且它需要一个用户开关，这开关会把一个背景透明的页面变成一块黑屏。收益不清楚的设置不加。*可配置的重载策略*：从来没人要过，是在这里想出来的，是一个找不到抱怨的设置。

## 5. 块：把页面当成桌面的一部分（L 系列）

缩放已经回答了*页面的哪一部分*，并把那一部分铺满整块屏幕。另一半是*它落在桌面的什么位置*——一块放
大后的碎片通常不是你想要它有全屏那么大的东西，而是你想放在角落的东西。

于是：一个网站变成一个块。它的内容就是缩放已经产出的东西；它的位置和大小是新的，而且自由——同时提
供一个四宫格，让摆一个块变成在四个明摆着的答案里挑一个，而不是一次拖拽练习。

```
今天                         一个块                      宫格
┌───────────────────┐        ┌───────────────────┐       ┌─────────┬─────────┐
│                   │        │            ┌────┐ │       │         │         │
│   放大后的区域    │        │    桌面    │ A  │ │       │    1    │    2    │
│   铺满            │        │            └────┘ │       ├─────────┼─────────┤
│   整块屏幕        │        │  ┌────┐           │       │    3    │    4    │
│                   │        │  │ B  │           │       │         │         │
└───────────────────┘        │  └────┘           │       └─────────┴─────────┘
                             └───────────────────┘        吸附，并可选择
                                                          避开 Dock
```

宫格的四格可以取自整块屏幕，也可以取自 Dock 让出来的那块区域——这是个设置，因为答案取决于某人把
Dock 放在哪、以及它是否自动隐藏。这个区别代码里已经有了（`screen.pageFrame` 对 `visibleFrame`）；只
是从没提供给用户。

**为什么值得做。** 一个块加一次缩放，就把网站变成了桌面小组件。具体的例子是一个只存在于网页上的数
字——这个月的 Codex 或 Claude 额度用掉了多少。没人会为它做一个小组件。缩放到那个数字，把块放到角
落，桌面其余部分还是桌面。这是一类东西：一块构建面板、一个部署状态、一个倒计时、某个页面上的一个数
字，永远不会有人为它写一个 app。

**大部分已经存在**，这是做它的主要理由。一个 scene 拥有一个窗口；`Zoom` 挑出页面的哪一部分；
`DesktopWindow` 设置任意 frame；多个 scene 可以同时跑。直到这周，裁剪*确实*会把窗口缩到自己那么大；
那个已经移除了（见下面三个问题里的第一个）。这一节把第二件事带回来，并给它一个主人。

| | 事项 | 状态 | 备注 |
|---|---|---|---|
| **L0** | 用移动壁纸的方式选一块区域，而不是在它上面画一个框 | **已完成** | 见下文。K2 跟着一起没了：已经没有矩形需要转换 |
| **L1** | 一个网站在它的显示器上有位置和大小，而不只是有一块显示器 | 待办 | 存成分数，就像 `Zoom` 存一个中心点和一个放大倍数那样，这样一个块能活过显示器更换 |
| **L2** | 一个可吸附的四宫格，以及给其他情况的自由摆放 | 待办 | 宫格是可供性，不是模型。自由摆放才是模型 |
| **L3** | 宫格用整块屏幕还是让开 Dock | 待办 | 一个设置。`pageFrame` 和 `visibleFrame` 都已经算好了 |
| **L4** | 点击落到哪个块上 | 待办 | 浏览模式和按住交互现在的意思都是「壁纸」。有了块，它们就必须指其中某一个 |

### L0 的完整说明

一个区域存的是一个中心点和一个放大倍数。它过去是靠在壁纸上拖一个锁定长宽比的矩形来*选*的，最后再转
换成存储的形状。这个落差带来三个问题：

- **你是在你正在框的东西上画。** 矩形不是结果；你看着一个轮廓，去想象它会变成什么。
- **只有一次机会。** 画歪了就得重来，已有的区域也没法调整——`beginCropSelection` 会先把它清掉，这是
  故意的，否则你就是在框一个区域的区域。
- **K2 就住在那次转换里。** 一个对着窗口量出来的矩形，变成一个对着页面量出来的分数，两者对不到像
  素级。

直接操纵把这三条一起消掉，因为它*就是*存储模型本身：拖动移动中心点，滚动或捏合改变放大倍数，壁纸每
一刻都在显示结果。回车保留，Escape 还原。什么都不用转换，所以 K2 无处发生，而调整一个区域和新建一个
区域是同一个手势。

那层覆盖层留着，工作从画矩形变成吞掉滚动和拖动，让它们作用于区域而不是页面：在一个自己会平移的页面
上，floor796 或一张地图，手势必须移动的是取景框，不是框里的内容。

块要的是同一套交互（L1–L3）：摆放一个块和调整它的大小，就是这两个手势作用在另一个矩形上。为区域先做
一遍，正是先做它的理由。

**用哪些手势，以及为什么不冲突。** 对触控板来说这个担心是真的——同样两根手指怎么既平移又缩放——但
macOS 本来就把它们分成了两个手势。~~而且 Apple 早就发货过一模一样的交互：一个锁定长宽比、取景框不能
动的裁剪，就是「照片」的裁剪、iOS 的照片裁剪，以及每一个头像选择器，取景框不动，内容在它下面动。~~
**这段写在 L0 发布之前，而 L0 发布出来的是反过来的。** 在这里让内容动是错的，理由对一张照片不成立：
网页自己会平移和缩放，所以在 floor796 或地图上，一幅会动的画面有两种读法，而页面自身的放大倍数会和
取景框的相乘。静止的页面加会动的取景框只有一种读法。手势冲突那段论证仍然成立，下面这张表也是实际发
布出来的样子，但那个前提和代码是反的；`Zoom/CropSelectionView.swift` 里写着取代它的那套推理。**L 系
列里任何继承了「同样两个手势作用在另一个矩形上」的东西，要继承的是已发布的模型，不是这一段。**

| | 平移 | 缩放 |
|---|---|---|
| 触控板 | 双指滚动 → `scrollWheel(with:)`，`hasPreciseScrollingDeltas == true` | 捏合 → `magnify(with:)`。不同的手势，所以两者甚至可以同时发生 |
| 鼠标 | 拖动，或滚动 | 滚轮。滚轮鼠标上没有捏合，而缩放正是滚轮以外别无他法可达的东西——Apple 地图和 Google 地图都是这么判的 |
| 键盘 | 方向键 | `+` / `-` |

`hasPreciseScrollingDeltas` 把两种设备区分开，所以滚动在触控板上是平移、在滚轮上是缩放，不用问用户
手上是哪一种。**拖动在任何设备上都是平移**，所以一个从没发现过手势的人照样能用这个东西。

覆盖层必须做对的两个细节。`webView.allowsMagnification` 是开着的，所以传到页面的捏合会缩放页面——覆
盖层必须把 `magnify(with:)` 也吞掉，不能只吞 `scrollWheel(with:)`。另外这个模式得说明自己是什么：一
个小面板，显示当前放大倍数，回车保留，Escape 还原。~~缩放应该跟随指针而不是跟随屏幕中心~~ ——**被同
一次反转推翻。** `Geometry.resizedFrame(byGrowing:)` 是故意绕着 frame 自己的中点长大的：页面不动，动
的只有取景框，而把尺寸变化锚在指针上会把取景框从指针底下抽走。跟随指针的缩放在画面会动时感觉对，在
画面不动时感觉错。

**让这件事比看上去更难的三样东西**，现在就点名，免得以后才发现：

- **两样东西在决定同一个窗口的大小。** 今天窗口的 frame 归可见性策略所有（`DesktopWindow.reducedRegion`）。
  块也要它——正是这场冲突让裁剪和可见性策略一直打到裁剪干脆不再移动窗口。所以一个块必须是窗口的*基
  准* frame，遮挡在它里面往里缩，绝不能反过来。
- **一个块一个 web 进程。** 三个块就是三个 `WKWebView` 和三个 web 进程。P 系列的存在就是为了不为没
  人看的渲染付钱，而这件事把账单乘了上去。这让快照后端更重要而不是更不重要：一个只显示一个数字的
  块，是这个 app 里「给页面拍照而不是跑着它」最清楚的场景。
- **块不是一个用户能抓住的窗口。** 那底下没有标题栏，而加上标题栏就把壁纸变成了 app。摆一个块只能像
  框一个区域那样发生——在壁纸上操作，桌面仍然在后面可见——或者从一个宫格位置的菜单里选。

## 5.5 页面记得什么，以及谁在记（M 系列）

声音和框好的区域属于网站，跟着网站存。*页面*当时在哪儿——floor796 的镜头、一张地图的视口、一块仪表
盘往下滚了多远——属于页面，而页面有四种方式可以记住它。其中三种已经能活下来；知道哪种是哪种，就是答
案的大部分。

| | 页面把自己的位置存在哪 | 能否活过一次重启 |
|---|---|---|
| **M1** | `localStorage` / IndexedDB | **能，但不是这一行原先给的那个理由，而且这个保证现在更窄了。** 它原先说 `WKWebViewConfiguration()` 默认用持久化 store。现在不是了：`createWebView` 赋的是 `DiskBudget.store(for: website.id)`，所以每个网站拿到自己的持久化 store，floor796 仍然能拿回它的 `last-pos`。变的是范围——**`localStorage` 现在按网站条目分区，不是按 origin 分区。** 两个指向同一站点的条目（比如一块显示器一个）不再共享登录态或保存的位置，而删掉一个条目再把同样的 URL 加回来会是空的，因为 `removeOrphanedStores` 会在下次启动时回收旧 store。这是让一个网站的磁盘开销随网站一起消失所付的代价。同一笔交易的好处一面：「清除网站数据」不再是回收它的*唯一*办法——删掉那个网站也能回收，而且不会把用户从他们留下的那些网站里登出 |
| **M2** | URL fragment | **能，现在能了。** 页面自己移动到的那个地址记在网站自己那个地址旁边，绝不覆盖它，而且只在两者除了 fragment 之外完全相同时才用。fragment 不会 404，这就是检查到此为止、没有把 query 一起放行的原因。和 M3 共用「把页面放回原处」这个开关 |
| **M3** | 文档滚动 | **重载时能** ——`ScrollRestoration` 在重载前一刻捕获、重载后放回。硬退出最多丢掉最后一次滚动，因为后台没有任何轮询来支撑它 |
| **M4** | 只在内存里 | **不能，而且没有办法。** 一个把镜头存在变量里、哪儿都不写的 canvas，没法问它刚才在哪 |
| **M5** | 一半在地址里，一半在内存里 | **一半。** floor796 就是这一类，而它自己的几个值得读一读：`restorePositionFromUrl: true`、`restorePositionFromLS: false`，还有一个两边都没有的 `_matrixPosition._zoomFactor`。所以*在哪*回来了——fragment 是这个站点唯一支持的路子，也正是 M2 恢复的那条——而*多近*没回来。人看到的是这两样合在一起，所以只拿回一样，看着还是不对 |
| **M6** | 不去记住页面，直接把页面留着 | **在 app 的一次运行之内是完整的，出了这次运行什么都没有。** 一个从没被拆掉的页面什么都不丢——位置、放大倍数、滚动、登录、动画状态，站点记什么、记在哪都一样。但它是内存，所以退出、重启或禁用都能和一次重载一样彻底地结束它。它回答的是「切走再切回来」，也就是人们每小时都会遇到的那种情况，并顺手用它回答了 K3，因为切回来不是一次页面加载。它不回答「明天打开这台 Mac」。页面被留着多久就多一个 WebContent 进程，所以它应该是一个按网站的开关，而不是一条策略 |

**这件事现在的状态：暂时不做更多。** M2 已发布，所以位置会回来，而 floor796 自己的放大倍数不会。绕过
它的两条路都成立，也都不急：

| | | 买到什么 | 代价 |
|---|---|---|---|
| **A** | 就这样放着 | — | 位置会回来，放大倍数永远不会 |
| **B** | M6，做成按网站的开关 | 切换时一切都留住，而且切回来变成瞬时的（K3） | 页面留着期间多一个 WebContent 进程；退出即失 |
| **C** | 站点条目上的 `pageWorld: true` | 站点自己的放大倍数能活过一次重启 | 那个条目失去隔离，而且它依赖 floor796 的私有字段，所以那边一改设计就废 |

B 和 C 不冲突。真要动，B 是更好的第一步：它不依赖任何网站的内部实现，帮的是所有站点而不是一个，而且
顺路关掉 K3。C 买到的东西更窄，钩子更脆。

**C 是唯一能活过重启的路子。** 按站点的自定义 JavaScript 被注入到 `.world(name: UUID())`，一个隔离的
world，所以它看不见 `window.floor796` 或任何别的页面全局变量，这就是一个站点条目读不到缩放、更别说
把它放回去的原因。注入到页面自己的 world，会让一个条目能把缩放存进 `localStorage`，那是在磁盘上，所
以它能比 app 活得久；M6 不行，它是内存。这件事最初写下来时把代价说重了：app 自己的脚本——那个音频控
制——在 `.defaultClient` 里，两种情况下都保持隔离，所以变的只是一个网站自己的条目能不能碰到那个网站
的全局变量。条目本来就包在一个 IIFE 里，不会意外往页面里漏东西，而且只在它被写出来的那个页面上跑，
别处不跑。真正的风险在反方向：页面可以重定义条目要去拿的东西，而对一张壁纸来说，这给攻击者的东西不
超过一个普通页面本来就能对自己做的。所以：按条目 opt-in，站点 schema 里的 `pageWorld: true`，默认隔
离，而不是把所有东西的 world 都改掉。这样谁审条目，谁就看得见哪些条目要了这个。

**M2 已经做出来了。** 手动版本本来就有——菜单里的「把网站更新为当前」把存着的网站指向当前加载的地
址——这既证明了人们想要它，也证明了这个机制能用。自动版本必须避开那个菜单项造成过一次的 bug：它对每
个带 host 页面的网站都触发，把其中一个变成了 GitHub 404。所以才是把最后加载的地址记在存着的那个旁边
而不是盖过去，而且只在两者除了 fragment 之外完全相同时才用。再多一点就是另一个页面了，而加载一个和
某人输入的不同的页面，正是那次 404 的来路。（这一段原先写的是「fragment 或 query」，而 M2 那一行写的
是「fragment」；`ScrollRestoration.addressToLoad` 在两边都比较 `normalized(removeFragment: true)`，没
给 `removeQuery` 传值，它默认是 false——所以 query 是被比较的，对的是那一行。）

也值得在 app 里某个地方明说出来：**一个网站自己的设置是按网站记的；页面在它自己内部的什么位置，由页
面说了算。** 这就是两个看起来一样的站点表现不同的原因，而现在没有任何地方解释这件事。

## 5.6 多显示器：做了，从没测过（D 系列）

**这里每一部分都是在一台单显示器机器上写的，从没在两块屏幕上跑过。** 这不是一份已知 bug 清单，是一
份没人核过的断言清单——而 D5、D9、D10 和 D11 是读代码核出来的，结果是假的，也已经修了，在信任这一列
其余部分之前值得知道这一点。中心点加放大倍数这个设计*正是因为*第二块显示器才存在的——在一块屏幕上框
好的矩形到另一种形状上不可能对——所以论证最充分的那个特性，背后的证据最少。

| | 断言 | 什么情况会说明它是错的 |
|---|---|---|
| **D1** | 每块显示器上一个不同的网站 | 两个 `display` 值不同的网站给出两个 scene。`display` 为 `nil` 的网站跟随「设置」，所以两个这样的网站会落到同一块屏幕上，其中一个不显示。**由 D9/D10 部分回答：** 每块显示器挑哪个网站现在是按显示器算的，也有测试；至于每块显示器接下来是不是真的*渲染*了对的那一个，仍然没人看过 |
| **D2** | 在一块显示器上框好的区域，到另一块上仍然是对的 | **几何那一半已经看过，是成立的。** `CurrentWebsiteTests` 覆盖了「在 16:10 上框、在 16:9 上显示」：`Zoom.region(inPageOfSize:)` 从页面被*显示*时的尺寸推出区域的形状，所以区域永远是当前显示器的形状，而 `magnification` 是从被夹紧之后的区域反推出来的。没人看过的部分需要两块显示器，而且比原先小了：移动之后 `pageLayoutSize` 会不会拿到新屏幕的 `pageFrame`，以及 `PageView.layOutContent` 会不会在 `installContentView` 之后从 `bounds` 重新推导 |
| **D3** | 框选发生在网站所在的那块显示器上 | **开头没问题，收尾有个洞。** `beginCropSelection` 按网站 id 匹配 scene，而 `currentWebsite` *就是* `primaryScene.website`，所以正常路径不可能挑错 scene。但 `finishCropSelection` 是靠 `croppingSceneDisplay` 加一个 `?? primaryScene` 兜底找回去的——所以如果那块显示器在拖动中途被拔掉，*主* scene 会被恢复层级和交互性，而被框的那个 scene 停在 `.floating`、`alphaValue = 1`。这是 app 里唯一一条能把窗口永久钉在所有东西之上的路径。见 K12 |
| **D4** | 菜单栏色带，在一块没有菜单栏的显示器上 | `installMenuBarBandIfNeeded` 在 `menuBarHeight` 为 0 时拒绝，而第二块显示器就是这种情况，除非「显示器有单独的空间」开着。那个开关会改变答案，两种状态都得看 |
| **D5** | ~~运行期间插拔~~ | **读代码核过；在三个各自独立的地方是假的。现在是 K13、K14、K15。**「离开的显示器对应的 scene 会被拆掉」并不是实际发生的事：`displaysInUse` 读 `website.effectiveDisplay` 而不问那块显示器还在不在，所以 `rebuildScenes` 把那个已离开的 scene 继续当成需要的，而 `DesktopWindow.setFrame` 和 `WallpaperScene.screen` 都会回落到 `.main`——两个全屏壁纸窗口叠在内建显示器上，各带各的定时器和菜单栏色带。`Display.withFallbackToMain` 就是为这个存在的，而它只在「设置」里被调用。一台笔记本每次脱坞都会撞上这个，而且**不需要两块显示器就能复现**：接一块，把一个网站指到它上面，拔掉 |
| **D6** | 不同缩放因子、不同尺寸并排 | 页面按每块屏幕的 `pageFrame` 排版，所以一块 Retina 和一块非 Retina 应该各拿各的。从没见过 |
| **D7** | 同一个网站在两块显示器上时，页面当时在哪 | **这里论证的那个保护并不保护这件事。** `displaysInUse` 是按*网站条目*去重的，所以它保证的是一个**条目**到一块显示器。三个按页面存的家族是按 **URL** 做 key 的——两个 id 不同、URL 相同的条目，一块屏一个，这是合法的，而它们会互相覆盖对方的 `scrollPosition_`、`lastAddress_` 和 `zoomLevel_`。自 PR #10 起数据 store 是按 `website.id` 做 key 的，所以这个 app 在两套坐标系上跑着两套持久化方案。把它们重新按 `website.id` 做 key 能一起解决，代价是保存的位置丢一次 |
| ~~D8~~ | ~~「在所有空间显示」和播放列表，按显示器分别生效~~ | **由 D9 回答，而它并不工作。** 两个 scene 各按自己的定时器轮换，在任何机器上都不可能工作过：它们轮换所依据的那个标记是一个全列表清空的 flag。已修，并由 `CurrentWebsiteTests` 覆盖。~~按显示器的「在所有空间显示」仍然没人看过~~ ——**它不需要看，它需要读，而且它是坏的：K15——那一条现在也被划掉了，因为那个设置没了，`.canJoinAllSpaces` 挪进了 `DesktopWindow.init`。** `DesktopWindow.init` 的 `collectionBehavior` 里不含 `.canJoinAllSpaces`；唯一会加上它的是 `Defaults.publisher(.showOnAllSpaces)` 的处理器，它遍历的是它触发那一刻已经存在的 scene。启动顺序让这件事在启动时是对的，对之后建的每一个 scene 都是错的 |
| **D9** | ~~一个全列表清空的 `isCurrent` flag，撑着一套按显示器的轮换~~ | **已修。** `advance(on:)` 和 `scheduled(for:)` 按显示器分组，但 `makeCurrent` 会把每个网站的 flag 都清掉，所以每块显示器的播放列表滴答一次就抹掉另一块的标记；那块显示器读到「没有当前的」，从索引 0 开始数，永远走不过它的第一个网站。下一个、上一个、随机、声音、选择区域和「在所有空间显示」都通过同一个 flag 起作用，所以每一个都是悄悄作用在最后持有它的那块屏幕上。现在按显示器分了，规则以纯函数的形式放在 `Support/Rotation.swift`，这样 `swift test` 就能覆盖两块显示器的情况，而不用真的拥有两块显示器 |
| **D10** | ~~每个 scene 的 web view 都按全列表的当前网站来配置~~ | **已修。** `createWebView` 读 `WebsitesController.shared.current` 来取自定义 CSS、自定义 JavaScript、反色、打印样式和 Google user-agent 那个特例——在创建时烤进去，之后再不复查。在一块显示器上那就是这个 scene 自己的网站，所以从没显形；在两块上，第二块显示器的页面跑的是第一块的代码。音频设置、自签名证书的处理，以及页面右键菜单里的「把网站更新为当前」也一样。现在 scene 在 `init` 里就被交给它的网站，在 web view 存在之前 |
| ~~D11~~ | ~~页面按它启动时所在的那块显示器排版，移动之后仍然如此~~ | **核过，并没有在发生。** `PageView` 确实从 `init` 缓存了 `pageSize`、区域和放大倍数，但一次显示器变化会走 `NSScreen.publisher` → `rebuildScenes` → `installContentView`，而给 `content` 赋值会在 `layout()` 有机会用上过期数字之前重建视图，所以那份缓存在过期之后从没被读过。还是删了：`layOutContent` 现在从 `bounds` 推导，因为一个视图被实时传入的值，再缓存一份副本，对下一个给壁纸窗口加改尺寸理由的人来说是个陷阱。原来那条断言是对着一个文件推出来的，读一遍调用方就活不下来 |

日常使用找到这些比推理快——但有四条（D5、D9、D10、D11）是读出来的而不是用出来的，而 D2 和 D8 结果根
本不需要第二块显示器（第 3 节写了一直出错的是什么）。真正剩下的需要硬件：D1、D4、D6，以及 D2 剩下的
那两半。

## 5.7 站点目录：没人审过（S 系列）

三份清单、一条流水线，和一个哪一份都还没看过的维护者：

```
sites/CANDIDATES.md      一个链接池，比目录大，而且本来就该一直比目录大
      ↓  有人把设置调出来，并验证成立
sites/*.yml               经 schema 校验的条目，出现在 app 的站点图库里
      ↓  被挑进「值得随包发布」的那几条
featured: true             8 条，首次启动时装好
```

流水线是对的，问题在数字上。每一条条目都是由一个 agent 从一个链接加一个猜测写出来的，而在陌生人首次
启动时自己装上去的那 8 条，是整个 app 的第一印象。

| | 事项 | 状态 | 备注 |
|---|---|---|---|
| **S1** | 维护者审那 8 条 featured | 待办。**这条最先** | 新用户在判断这个 app 好不好之前看到的东西。八个页面是一个晚上的事，也是这一节里价值最高的一小时 |
| **S2** | 维护者审另外 30 条 | 待办 | 赌注更小——得有人特意去找才看得到——但它们带着同一个断言：上面的设置是对的 |
| **S3** | 候选池里大部分从来没有毕业过 | 永远待办 | 这不是一个要清空的积压。链接便宜，条目是活，所以池子比目录大是常态，不是欠账。确切数字在这里故意不写：它随每一次贡献变动，而写进正文的数字就是会出错的数字。**这条规矩写下来之后就在同一节里被破了**——上面三段里的计数，等到有人去核的时候三个数字全都漂了。它们现在是被删掉而不是被更正的，那本来就是这条规矩一开始要求的做法 |
| **S4** | 三份清单里，哪一份是给读者的事实来源 | 答了一半 | `CANDIDATES.md` 是池子，`sites/*.yml` 是目录，`NOT-INCLUDED.md` 是拒绝记录。两份 README 现在都直接链到 `CANDIDATES.md`，所以读者不再被丢到目录里自己猜——这一半做完了。剩下的是：一个落在 `sites/` 的读者仍然先看到贡献指南，还得自己弄明白它旁边哪一个才是 app 实际提供的那份清单 |

**不加文件也能简化 S4 的办法。** 站点图库里已经正好展示那 38 条，带着它们的设置，可按标签过滤——那是
可读的清单，而且是在唯一一个「选中一条会有效果」的地方。仓库不需要同一份数据的第四种呈现；它需要的是
那两个 markdown 文件把自己是干什么的说清楚，别再读起来像是 app 的替代品。

## 5.8 面板的媒体控制（V 系列）

面板已经知道视频在哪儿了——它从页面里读 `currentTime` 和 `duration` 再写回去，好让同步的几块显示器保
持一致。一套传输控件需要的东西都在手上；缺的是控件本身，以及「哪些页面配有它们」这个决定。

| | 事项 | 已知的部分 |
|---|---|---|
| **V1** | 在那一列上暂停、播放、后退或前进一步 | 那个时钟已经在报 `duration`，所以一个页面要么有视频要么没有，没有的时候控件干脆不出现就行。`MediaSync` 已经在写 `currentTime`，所以步进和它纠正漂移时发的是同一个调用 |
| **V2** | 画面下方一条进度条 | 同一份读数驱动它。它得在面板打开时更新、面板关闭时停下——面板是临时的，而一个活得比它久的定时器就是一个没人关掉的定时器 |
| **V3** | 在一个同步组里，一个控件意味着什么 | 把一对同步显示器中的一块暂停是自相矛盾的：跟随者每五秒被朝领头的方向纠正一次，会被拽回播放。在任何成员上按下的控件都必须作用于整个组，这就让组而不是显示器成为传输控件作用的单位 |
| **V4** | 直播没有传输控件 | 直播上的 `currentTime` 是相对于一个滑动窗口的，seek 经常被拒绝，而「后退三十秒」可能根本不存在。这些控件必须是缺席，而不是在场但坏掉，而判断它的条件和「有没有视频」不是同一个 |
| **V5** | 保存某一列正在显示的画面 | 那一列上的一个按钮把当前帧写到桌面，而按住超过一秒则改写一小段 GIF。**用显示器自己的分辨率，不是面板的。** 面板拍快照用的是 260 点，因为它只画那么大——照同样方式取的一帧会是个缩略图，所以这需要第二次全尺寸快照，只在被要求时才拍。别把这两条路径搞混：便宜的那条在面板打开时每秒跑好几次，贵的那条只跑一次，而在它还是默认路径时每帧要花约 600ms |

这些东西需要、而现在还没有的两样。那个时钟按五秒一拍报领头的位置，用来纠正漂移是对的，用来驱动进度
条则慢得远。传输控件想要自己那份更快的读数，而且只在面板打开时要。

还有，GIF 需要的是把帧留住而不是显示出来。面板的快照是故意做成临时的——每次刷新替换掉上一张，之前的
图像被释放，这就是连续刷新四十五秒对 app 内存的影响小于它自己波动幅度的原因。录制必须把它们留着，按
全分辨率，留满按住的整段时间：一块 4K 显示器一秒是几十兆，所以它想要的是一个帧预算和一个硬停止，而不
是「直到用户松手」。

## 6. 已知且尚未修（K 系列）

在使用中报告、复现过、暂时放着。每一条写下来而不是修掉，是为了让第一个版本成为一个真的存在的东西。

| | 发生什么 | 关于它已知的部分 |
|---|---|---|
| **K1** | 一个 YouTube 视频没法缩回 YouTube 页面里，所以没有办法登录 | 地址被改写成只有播放器的那个页面，再用一个宿主页面框起来，因为 YouTube 的播放器在自己是文档、而不是文档里的一个 frame 时会回「error 153」。这把视频弄上去了，也把站点一起带走了：播放器周围没有页面可以导航，浏览模式也没有东西可以点进去。Bilibili 的播放器是一个普通页面，这就是两者不同的原因。任何修法都得让 153 别回来。**「没有办法登录」说得太重了。** 地址是网站上的一个普通字段，而 cookie 现在存在一个按 `website.id` 而不是按 URL 做 key 的 store 里——所以把地址改回 `youtube.com/watch`、通过浏览模式登录、再把地址改回嵌入版，会话是保住的，因为地址变了 store 不会跟着变。没人被告知这一点；最便宜的修法是一句帮助文本，不是新 UI |
| ~~K2~~ | ~~框好的区域没有正好落在框它的地方~~ | **由 L0 修掉。** 那个落差就是 L0 第三条里描述的那次转换。移动页面直接改的就是存下来的值，移动页面直接改的就是存下来的那个值，没有转换，也就没有什么会差出一个点。区域现在也能活过任何一种退出这个模式的方式，而且不再重载它正在框的那个页面 |
| **K3** | 切换网站可能要好几秒 | 那是一次页面加载，而交换式加载在整个过程中保持前一个页面在上面，所以没什么坏掉——但没有任何东西告诉用户它在工作，而选了网站之后好几秒壁纸没变，读起来像是这次选择没生效 |
| **K4** | 没人看的时候，没有任何措施降低这个 app 的开销 | 暂时是故意的。见第 4 节 |
| **K5** | 没有办法在 app 内部选择它的语言 | 它跟随系统。macOS 有一个按 app 的设置——系统设置 → 通用 → 语言与地区 → 应用程序——今天就能用，但没人找得到：一个把 Mac 跑在英文下、想让 Nifro 说中文的人，没有理由想到答案在系统设置里三层深的地方。在「设置」里放一个写 `AppleLanguages` 并提议重新启动的选择器，成本很低 |
| **K6** | 措辞有的地方对，有的地方单薄 | ~~现在每一个设置都说明了它做什么~~ ——数过了，这说得乐观：`Screens/` 下一共七处 `SettingHelp` / `.help(`，对着两屏共 25 KB 的设置。已有的那些是一条一条写出来的，看得出来：有的解释机制，有的解释后果，少数两样都有但长度不一。值得当成一组而不是二十个各自的答案，通读一遍 |
| **K7** | 任何地方都没有处理 HDR | 这个 app 里没有一行碰它：一个页面的 HDR 内容会被 WebKit 怎么处理，全看它，而没人测过那是什么。壁纸整天在屏幕上，所以搞错了就整天看得见。在设计任何东西之前，需要一个真的 HDR 源，以及看一眼实际到达显示器的是什么 |
| **K8** | 一条 Bilibili 条目显示的是通用图标，而一条 YouTube 条目显示的是视频自己的封面，**只在「网站」列表里** —— `previewImageURL` 只有一个调用方，`WebsitesScreen` 里的那一行图标，所以站点图库不受影响 | YouTube 在一个由视频 id 推出来的固定地址上发布封面，所以不花什么代价。Bilibili 的封面在 `api.bilibili.com` 后面，是一次网络请求加一个 JSON 字段（`data.pic`），而不是一个你能拼出来的 URL。值得做，但这会是 app 第一次去调用一个站点的 API，而不是只加载一个页面 |
| **K9** | 目录里一条带 `zoom` 的条目，会悄无声息地干掉每一份已安装副本上的实时站点图库 | **读出来的，从没触发过，而且四道 CI 关卡全都放行。** `sites/index.json` 的两边对「一个 `Zoom` 怎么拼」有分歧：Swift 合成的 `Codable` 把 `CGPoint` 编码成一个无 key 的数组，所以它要的是 `{"scale":2,"center":[0.5,0.4]}`，而生成器和 `schema.json` 产出的是 `{"centerX":0.5,"centerY":0.4,"scale":2}`。往返验证过：解码生成器那个形状会抛异常。生成出来的 Swift 路径没问题——它直接构造 `Zoom(center:scale:)`——这就是本地构建从来看不到它的原因。`SiteCatalog` 随后在一个 `try?` 下面一次性解码 `[Entry].self`，所以**一条坏条目就丢掉整次拉取**，回落到内置快照，报 `isLive: false`，什么都不说。今天没有条目用 `zoom`，所以第一个加上它的贡献者会把所有人的都弄坏。两个修法，第二个更要紧：把 key 映射上，以及别再让这条路径是全有或全无的 |

| **K16** | 同步一块显示器会吃掉它上面原来的网站，而且每次都留下一个副本 | `mirrorAcrossSyncGroup` 就地覆盖跟随者已有的条目——`update(existing.id) { $0 = copy }`——所以那块显示器原本在显示的页面是没了，不是被搁到一边，也没有退路。跟随者上没有条目时它改为追加一个新的，而没有任何东西会删掉这些，所以一个列表每块显示器每个组就多攒一份领头网站的副本。在维护者自己的列表上实测：八条条目，其中六条是两个网站的副本，两个原件（Calculating Empires、WindowSwap）被覆盖且不可恢复。两半是同一个决定——一条镜像条目是领头那条的一个*视图*，不是一个自身独立的网站，它根本就不该出现在列表里 |
| **K17** | 一块显示器上的网站选择器只列出那块显示器自己的网站，而那通常只有一个 | `DisplayPanelModel.refresh` 把 `choices` 构造成 `all.filter { $0.effectiveDisplay == scene.display }`，所以一个网站只有在已经属于那块显示器之后才进得了菜单——而一个网站获得显示器的方式，就是在那里被选中。只有一个网站的显示器有一个只有一项的菜单，读起来像是「这个选择器不工作」。这个控件是用来选任意网站*并且*把它挪到这里的，所以列表想要的是所有网站，已经在这里的做上标记 |

| **K19** | 新装的 app 打开时屏幕上什么都没有——**已由别人在修，不要接手** | 没有初始配置，所以新用户看到的第一样东西是一张不在那儿的壁纸。它应该带着已经在列表里的网站发货，静音，按这个顺序：**floor796**、**Svalbard**、**Calculating Empires**——单显示器时 floor796 上，有两块时第二块上加 Svalbard。静音是因为一张装上去就出声的壁纸是一张会被卸载的壁纸。这三个都已经在 `sites/index.json` 里，也都已经带着 `audio: muted`，所以这是一个读目录的首次运行步骤，不是新条目 |

## 8. 签名与分发

从查 [AeroSpace](https://github.com/nikitabobko/AeroSpace) 实际怎么做得到的：

| | AeroSpace | Nifro | 理由 |
|---|---|---|---|
| 签名 | 机器上的一张自签名证书 | 同样，`Nifro Signing` | 对 Gatekeeper 来说两者一样，但身份不一样：一张稳定的证书让 app 的 designated requirement 保持稳定，而那些持有本地文件壁纸的 security-scoped bookmark 是和它绑的。ad-hoc 每次构建都换身份，把它们弄坏 |
| 公证 | 不做 | 有账号之后就做 | Nifro 是一个沙盒 GUI app，而它的用户不像平铺窗口管理器的用户那样习惯敲 `xattr` |
| 发布 | 一个本地脚本，加手动拖 zip | 一个 tag 触发 Actions，每种架构一个 dmg | 从本地机器发布不可复现 |
| cask | 一个单独的 tap 仓库 | 本仓库里的 `Casks/`，由 CI 回写 | 少维护一个仓库 |
| livecheck | 无 | 有 | 以后要是进了 homebrew-cask 主仓库会有用 |

**设计**：一个 workflow，按 `secrets.MACOS_CERTIFICATE_P12` 存不存在挑自己的路径。现在没有付费账号也能发布；以后买一个需要 6 个 secret 加上从 cask 里删掉 `postflight` 块，而一行 YAML 都不用改。

对用户的差别：

| | 用 brew 装 | 下载 dmg 双击 |
|---|---|---|
| 有账号（已公证） | 没事 | 一次「来自互联网」的确认 |
| 没账号（ad-hoc） | 没事（postflight 剥掉隔离属性） | **直接被拦**，只有「移到废纸篓 / 取消」 |

所以只要还没有账号，README 的安装一节就必须把 brew 放在最前面。完整手册在 `docs/RELEASE.md`。

**关于这个 tap 的两件事，目前都是故意的：**

cask 就放在本仓库里，所以安装意味着要点名 tap 的 URL：`brew tap PathGao/tap
https://github.com/PathGao/Nifro && brew install --cask nifro`。简写 `brew install --cask
PathGao/tap/nifro` 会解析到一个字面上叫 `homebrew-tap` 的仓库——多一个要养的仓库，外加在这里放一个对
它有写权限的 token。真要做，理由是另一条而不是那个简写：tap 会把本仓库克隆下来，整整 6 MB 的源码和图
片，装到每个用户的机器上，而且每次 `brew update` 都重新拉，而一个专门的 tap 仓库只有几千字节。等用户
多到这笔带宽是别人的问题、而不是一个整洁性论证的时候再做。

普通的 `brew install --cask nifro`、完全不用 tap，意味着要进 Homebrew 自己的 cask 仓库。那有一道热
度门槛——75 个 star，或 30 个 fork，或 30 个 watcher。今天两个 star。这是一个值得注意的里程碑，不是一
件要排期的任务。

**发布不可变性是关着的，目前是故意的。** 开关在 设置 → 通用 里，一个不在侧边栏的 Releases 标题下面，
它禁止改动已发布 release 的资产和 tag。终局是对的，今天是错的：README 里那两个下载链接能用，只因为
v0.1.0 的资产在发布之后被*改过名*，把版本号从文件名里去掉了。等几个 release 发出去、事后都不需要动它
之后，再打开它。

### 知道有新版本（U 系列）

app 里没有任何东西知道存在一个 release。没有 Sparkle，没有检查，没有菜单项——唯一的升级路径是
`brew upgrade`，而且只对那样安装的人有效。从 README 拿了磁盘映像的人会一直停在他拿的那个版本，直到他
碰巧再访问一次仓库，而对一个开机自启、很少被特意打开的菜单栏 app 来说，那约等于永远不会。

| | 事项 | 状态 | 备注 |
|---|---|---|---|
| **U1** | 检查有没有新版本并说出来 | 待办。**这条最先做** | 一次对 `/repos/PathGao/Nifro/releases/latest` 的请求，把 `tag_name` 和 `SSApp.version` 比一下，在菜单里放一句「有 0.2.0 版可用」并链到那个 release。不需要依赖、不需要 entitlement、不需要密钥、不需要基础设施——release API 是公开的，本来就在那儿。它告诉 brew 用户去跑 `brew upgrade`，告诉直接下载的用户有东西可以下。需要一个不是「每次打开菜单就轮询」的节奏，以及一个关掉它的办法 |
| **U2** | 顺便也下载并安装（Sparkle） | 现在不做 | 比 U1 看上去多得多。Sparkle 需要一个要发布的 appcast feed，和一对用来给更新签名的 EdDSA 密钥——除了证书之外，还要再养一个签名身份，养到这个 app 的生命结束。一个沙盒 app 也没法替换自己；那要走 Sparkle 的安装器 XPC 服务，给一个「entitlement 列表短」本身就是特性的 app 再加 entitlement。**而且 feed URL 从第一个带着它发货的版本起就是永久的**：Markpad 已经换到第二个仓库所有者了，它的发布流程仍然在断言*旧的*那个 URL 提供本项目的 feed，因为 v2.7.0 之前的每一份安装问的都是那个地址，别的什么都不问。这个仓库改一次名是免费的；从更新 feed 指向它那天起就不再免费 |
| **U3** | 告诉 Homebrew 这个 app 会自己更新 | 只在有 U2 时 | 从 app 能替换自己的 bundle 那一刻起，cask 就必须写 `auto_updates true`。没有它，`brew upgrade` 和 app 会抢同一个 bundle，而 brew 对已安装版本的认知会变陈旧。U1 单独不需要这个，这是先从它开始的又一个理由 |

第一个从 U1 受益的版本是它发布之后的那个——0.1.0 的用户不会被一个还不会检查的 app 告知 0.2.0 的事。
这是一个「早做」的理由，不是一个「做好」的理由。

## 9. 明确不做（不要再提）

| | 提议 | 为什么被否 |
|---|---|---|
| **X1** | 换 web 引擎（Electron / Tauri / CEF） | WKWebView 是一个和 Safari 共享的系统进程；别的任何东西都更贵。问题在调度，不在引擎 |
| **X2** | 用纯 SwiftUI 重写 | 现在这套 `NSMenu` + `NSWindow` 又快又对；换成 `MenuBarExtra` 是退一步 |
| **X3** | Tuist / XcodeGen | `project.pbxproj` 是 873 行，离「冲突会变成灾难」的规模还差得远，而手动往里加一个文件是四行 |
| **X4** | 一个依赖注入框架、一个插件系统 | 没有第二个实现，所以那个抽象没有依据可建 |
| **X5** | 只用 CLT 作为类型检查关卡 | **试过，失败**：KeyboardShortcuts 用了 `#Preview`，那个宏插件只随 Xcode 发货，而命令行工具没法构建那个依赖模块。必须装 Xcode |
| **X7** | 摄像头 / 屏幕捕获输入（`getUserMedia`、`getDisplayMedia`） | 这个 entitlement 是按进程的，也就是永久给一个全天候渲染任意用户 URL 的进程访问摄像头的能力；一个壁纸 app 的权限列表越短，越容易核。采集卡合成属于 OBS，监控属于 NVR 客户端。上游 [#125](https://github.com/sindresorhus/Plash/issues/125)；完整论证在 UPSTREAM-ISSUES.md §4。它**技术上是做得到的**；拒绝的理由不是难度 |
| **X8** | 真壁纸那条路：把页面渲染成图片，交给 `NSWorkspace.setDesktopImageURL`（原 P6，也就是第 2 节里的 A2） | 从没做过，而且现在是拒绝而不是阻塞。它会终结这个 app。这样设的壁纸是一张图片：不能点、没有浏览模式、不能滚动、不能按住交互、什么都登录不了——而交互就是这个 app 本身。刷新它意味着重新渲染再设一次，而 macOS 会给这个过程做交叉淡入淡出，所以一个时钟会让整个桌面每分钟交叉淡一次。它需要的渲染器正是那个离屏渲染器，而对恰恰值得放上去的那些页面，它拍出来是空白（第 2 节）。反对它的还有：菜单栏颜色，已经解决了；Mission Control 和 Stage Manager 的行为；app 退出之后图片还留着；以及闲时功耗，没人测过。一个把网页变成壁纸图片的工具是一个真实的想法——它只是另一个程序，而且根本不需要一个菜单栏 app |
| **X9** | 把用户自己的 Chrome 窗口放到桌面层，而不是我们自己渲染页面——一个热键把它拿到前面来用，一个热键把它送回去，裁剪和全屏视频都保留 | **它要的这套交互模型已经发货了。** `DesktopWindow.isInteractive` 在 `.desktop` 和 `.desktopIcon + 1` 之间移动窗口，而 `HoldToInteract` 是同一个开关的「按住某个键」版本。唯一新的东西是引擎，而引擎正是它垮掉的地方。**没有任何公开 API 能设置另一个进程的窗口层级**：`NSWindow.level` 只作用于本进程拥有的窗口；辅助功能 API 有位置、尺寸和 `AXRaise`，但没有层级，也没有下沉；剩下的是对着一个我们并不拥有的 connection 调 SkyLight，那是 yabai 的路子——一个注入进 Dock 的 scripting addition——而它需要关掉 SIP 的一部分。一个壁纸 app 没法对任何人提这个要求。**放弃图标层能让它做得出来，也仍然不值得。** Chrome 的 `--app=` 模式给出一个没有标签栏也没有地址栏的窗口，上面盖一层透明的、吸走点击的窗格，让那个窗口永远不会被抬起，于是它沉到所有别的 app 底下，而裁剪则从一个负的 `--window-position` 加一个超大的 `--window-size` 里自然掉出来——页面按全尺寸排版，只露出一块区域，我们自己那套裁剪语义白拿。要它命的是：**壁纸的生命周期挪进了一个我们控制不了的 app。** 在 Chrome 上按 Cmd-Q 就结束了壁纸，Chrome 一次自动更新会重启它，一个崩溃恢复气泡会落在它上面。而 entitlement 列表会从四行变成完整的辅助功能访问，还得关掉沙盒。**改成把它投送过来更糟。** 用 CDP `Page.startScreencast` 投进我们自己的 `.desktop` 窗口能保住图标层，但受 DRM 的视频会因为输出保护而变成黑的——想要 Chrome 的那一个理由，正是活不下来的那一样——而且帧是 JPEG，所以动画恰好在这个 app 存在的那种场景下劣化，另外它需要开着 `--remote-debugging-port`，这等于把用户的整个浏览器身份交给 localhost 上的任何一个进程。**这个动机反正有更便宜的答案。** WKWebView 共享 Safari 的引擎但不共享它的身份：每个 app 在自己的容器里拿到自己的 `WKWebsiteDataStore`，所以什么都不会从 Safari 或 Chrome 继承过来——但它是持久的，所以通过浏览模式登录一次就一直有效，而 `ContentRules` 已经覆盖了任何人为这件事会去装的那一个扩展。另见 X1，这是它的一个更弱的形式，以及第 2 节的第二条不满，这个把它反了过来 |
